# ESP32-S3 Basics

## 工作流

1. 确认目标、ESP-IDF 版本、目标芯片和具体开发板；不要把通用 ESP32 或其他 S3 板的资料当成当前板级事实。
2. 先读取与问题直接相关的 `sdkconfig`、板级引脚定义、外设初始化代码和错误日志。没有这些证据时，明确区分“芯片能力”和“当前板可用性”。
3. 按问题选择最少的参考资料：
   - 芯片能力、启动脚、内存属性或 I2S 硬件限制：读取 `references/official-chip-notes.md`。
   - 外设选型、共享总线、任务或故障隔离：读取 `references/peripherals-and-debug.md`。
   - 查询任意 ESP-IDF 组件、函数、类型、Kconfig 或示例：读取 `references/esp-idf-api-index.md`，再使用其中与当前 IDF 版本匹配的官方目录。
4. 先锁定故障域或约束，再提出最小改动和验证方法。不能用日志或硬件观测验证的结论，应标注为待确认。

| 问题 | 必查项 | 最小验证 |
| --- | --- | --- |
| GPIO 或引脚规划 | 板级 pin map、启动脚、供电和电平 | 上电与复位后测量电平或读取外设响应 |
| I2C/SPI/UART | 引脚、模式/地址/波特率、共享 owner | 输出配置并完成一次目标设备事务 |
| I2S/音频 | 时钟 owner、采样率、位宽、slot、DMA buffer | 确认时钟参数与收发链路无错误 |
| 内存或 DMA | 分配能力、buffer 生命周期、task stack | 检查 heap capability、栈余量和错误日志 |
| FreeRTOS 运行时 | 优先级、阻塞点、队列/通知、watchdog | 记录任务状态与事件时序 |

## 说明与评审

- 默认优先使用 ESP-IDF 公开且与当前版本匹配的组件、驱动和系统 API，例如 `driver/*`、`esp_*`、`heap_caps_*` 与 FreeRTOS API；不要直接操作寄存器、ROM 函数、HAL 私有接口或复制 IDF 驱动内部逻辑。
- 查询 API 时以当前 ESP-IDF 版本的官方 API Reference 为准；索引未列出具体组件时，从其 API Reference 总目录继续定位，而不是推测函数签名或复制其他版本的示例。
- 只有在 ESP-IDF API 明确无法满足启动阶段、严格时序、性能或芯片特性需求时，才下沉到更低层；说明无法满足的具体约束、所依赖的 IDF 版本和回归验证方式。
- 调试时先用 IDF 的错误码、日志、驱动状态和诊断 API 取得证据，再考虑读取寄存器；寄存器观测不能替代对初始化顺序或资源 owner 的检查。
- 将 Flash、PSRAM、IRAM、DRAM 的角色与当前数据或执行路径关联，避免脱离具体 buffer、task 或 ISR 的泛泛说明。
- 涉及 DMA 时，确认 buffer 的内存能力、对齐、生命周期和驱动要求；不要只因 buffer 较大就默认放入 PSRAM。
- 涉及跨任务状态、等待或资源仲裁时，优先建议 queue、task notification、event group 或 mutex，并说明对应的并发问题。
- 用短表或检查表表达结论；输出信号名、总线格式、配置键和实际文件路径。

## 外设与共享总线

- 从共享总线、pin mux、启动脚、时钟 owner、DMA、上拉与供电约束开始评审，而不是先选 API。
- I2S 必须确认播放与采集是否共享 BCLK/WS、是否同时活动，以及格式是否一致。变更共享时钟前，确认非活动端已完整停止并重新配置。
- SPI 必须分开检查总线级设置与设备级设置；共享 SPI 时检查 CS 和时序裕量。
- I2C 扫描只能证明总线有应答，不能证明目标设备的协议和初始化顺序正确。

## 故障隔离

- 按外设通信、时钟/格式、任务时序、内存分配的顺序缩小范围，一次只改变一个可验证因素。
- 先收集完整错误行、相关配置块、板级引脚定义和最短复现步骤。芯片能力争议以 Espressif 官方资料为准；板级电气行为以原理图、代码或实测为准。
- 区分栈溢出、watchdog、heap 耗尽和总线异常后再给修复建议，避免把所有运行时问题归因于硬件。

## 输出约定

- 先写结论、关键依据和最小验证；必要时再列出最高优先级的排查项。
- 引用确切文件路径、信号名、总线格式和 Kconfig/`sdkconfig` 键名。
- 对涉及启动脚、DMA、共享时钟或供电的建议，写清影响范围和硬件恢复方式。
